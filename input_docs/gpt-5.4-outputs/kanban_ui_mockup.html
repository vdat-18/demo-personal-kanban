UI mockup

Board-first project workspace with gated context + planning

Main anchor UX: Kanban board
Auxiliary systems: Directory + Planner
Closed states: Done + Cancelled

This mockup shows the full lifecycle you described: a project starts with only the directory tree unlocked for context gathering, then unlocks a planner chat, then unlocks the board. Once the board is active, every task uses the same lane-specific workbench: planning in Planning, execution in Doing, QC in Review, and output summary in Done. Moving a card to Cancelled also counts as closed.

Planner summary

This summary is the bridge between context intake and the kanban board.

Vision
Operate a profitable, weather-resilient lemonade stand that can serve concert traffic safely and quickly.
Key constraints
Possible evening rain, temporary staffing, supplier coordination, permit dependency, and peak demand near concert start.
Likely workstreams
Permits, procurement, staffing, stand setup, recipe/portion planning, weather contingency, and signage.
User decision point
If the user approves this summary, the kanban board unlocks and the planner seeds the first task batch into To do.

Requested context

The agent can explicitly call out gaps and link them back to the directory.

Missing or newly requested
Venue restrictions notice, permit status, cash handling policy, table layout sketch.
Documents already sufficient
Weather report, supplier contacts, temp worker list, lemonade recipes, event news article.
Recommended interaction: when the board unlocks, do not kick users into a separate product area. Keep the same shell and simply switch the main workspace from chat to the kanban board so the experience still feels board-first.

Design note
Closing the project should feel like a deliberate archival action, not just a status toggle. Show what will be preserved and who can still access it.

Close project

Tasks are fully closed. The user can now mark the project complete and preserve the final state.

Closure checklist

The final project close-out should verify that the board is truly complete.

All tasks are in Done or Cancelled.
Every Done task has an output summary.
Cancelled tasks have a reason recorded.
Key artifacts and deliverables are saved in the directory tree.

What gets archived

Preserve both the evidence and the execution narrative.

Project context
All uploaded and connected documents in the directory tree.
Planning record
Project vision, planner chat, and approval summary.
Board history
Task cards, movements, comments, QC states, and final summaries.
Completion rule
Tasks in Cancelled count as closed. The project close action should therefore use: Closed = Done + Cancelled. Only when every open task is exhausted should the project completion button become enabled.
